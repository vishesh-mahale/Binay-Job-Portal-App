### 💸 The Real-World Problem (Nahi Toh Hazaaron Rupees Waste Honge!):

Socho NestJS backend ne Google Cloud Tasks ko ek resume parse karne ka event bheja: `event_id = "evt_999"`.
Network glitch ya Cloud Tasks retry ki wajah se wo same event 2 alag-alag Cloud Run containers par **ek hi second mein 2 baar deliver ho gaya**!

Agar humne idempotency aur locking nahi lagayi hoti to kya hota?
1. Gemini / Vertex AI API ko **2 baar heavy LLM call** jaati ➔ **Double Cost/Money wasted!**
2. Dono containers ek saath Supabase DB mein `UPDATE` try karte ➔ **Database Race Condition & Deadlock!**
3. User ne apna profile 1 second pehle update kiya tha, aur background worker ne purana parsed data over-write kar diya ➔ **Stale Data Overwrite Bug!**

---

## 🛡️ The 3-Layer Defense Guard Architecture

Is problem ko permanent solve karne ke liye hamare worker mein **3 Layers ki Security Guards** lagi hui hain:

```text
Incoming Task Request (event_id="evt_999")
                  │
                  ▼
   ┌──────────────────────────────┐
   │ LAYER 1: Committed Event     │ ➔ Already completed in past?
   │ (`processed_events` check)   │    YES ➔ Return HTTP 200 (skipped=True)
   └──────────────┬───────────────┘
                  │ NO
                  ▼
   ┌──────────────────────────────┐
   │ LAYER 2: In-Flight Lease     │ ➔ Another worker processing RIGHT NOW?
   │ (`event_processing_leases`)  │    YES ➔ Return HTTP 200 (lease_held=True)
   └──────────────┬───────────────┘
                  │ NO (Atomic Lease Acquired!)
                  ▼
   ┌──────────────────────────────┐
   │ Heavy AI / Embedding Exec    │ ➔ LLM Call / pgvector 768-dim generation
   └──────────────┬───────────────┘
                  │
                  ▼
   ┌──────────────────────────────┐
   │ LAYER 3: Stale Revision Guard│ ➔ Did HR/User edit profile while AI ran?
   │ (`profile_revision` check)   │    YES ➔ Coalesce & Abort Write safely
   └──────────────┬───────────────┘
                  │ NO
                  ▼
        Atomic DB Transaction Commit!
```

## 🔬 Layer-by-Layer Deep Dive:

### 📍 Layer 1: Committed Event Check (`processed_events`)
📁 File Reference: [`app/repositories/processed_events_repo.py`](file:///c:/Users/ADMIN/OneDrive/Desktop/Vishesh/Binay-Job-Portal-App/07-fastapi-ai-worker/app/repositories/processed_events_repo.py)

Jab koi task successfully finish ho jata hai, to atomic transaction ke andar `processed_events` table mein row insert hoti hai:
`(consumer_name="fastapi-ai-worker", event_id="evt_999")`.

Agar Cloud Tasks 1 ghante baad galti se wahi message retry karta hai:
1. Worker check karta hai: `SELECT 1 FROM processed_events WHERE consumer_name = :c AND event_id = :e`.
2. Row milte hi worker AI API call karne se pehle hi **Instant HTTP 200 OK (`skipped=True`)** return kar deta hai.
3. **Outcome:** Zero AI API Cost!

---

### 📍 Layer 2: In-Flight Concurrency Lease (`event_processing_leases`)
📁 File Reference: [`app/core/database.py:L220-270`](file:///c:/Users/ADMIN/OneDrive/Desktop/Vishesh/Binay-Job-Portal-App/07-fastapi-ai-worker/app/core/database.py#L220-L270)

Agar 2 containers par ek hi millisecond mein same event aa gaya, to Layer 1 pass ho jayega (kyunki pehle kisi ne finish nahi kiya). Yahan **Layer 2 Lease Lock** kaam karta hai:

```sql
INSERT INTO event_processing_leases (lease_key, expires_at)
VALUES (:lease_key, NOW() + INTERVAL '5 minutes')
ON CONFLICT (lease_key) DO NOTHING;
```

* **Atomic Database Lock:** PostgreSQL row-level lock guarantee karta hai ki `INSERT` sirf **Ek Hi Container** ka successful hoga (Affected rows = 1).
* Jis Container 1 ka `INSERT` success hua ➔ Wo AI processing continue karega.
* Container 2 ko 0 rows returned ➔ Wo samajh jayega ki Container 1 abhi kaam kar raha hai, aur wo bina AI call kiye **HTTP 200 OK (`lease_held=True`)** return karke shant baith jayega!

### 📍 Layer 3: Stale Revision Guard (Coalescing Protection)
📁 File Reference: [`app/services/projection_service.py`](file:///c:/Users/ADMIN/OneDrive/Desktop/Vishesh/Binay-Job-Portal-App/07-fastapi-ai-worker/app/services/projection_service.py)

Socho Resume Parse karne mein Gemini AI ko 5 second lage. In 5 seconds ke dauraan candidate ne UI par jaakar apna Location/Phone number edit kar diya (Revision increment ho gaya `v1` ➔ `v2`).

Jab worker 5 sec baad AI result DB mein save karne aayega:
```sql
UPDATE candidate_search_profiles 
SET search_vector = :vec, embedding = :emb 
WHERE candidate_id = :cid AND profile_revision = :stored_revision;  -- v1
```
* Table mein ab `profile_revision` = `v2` ho chuka hai!
* `UPDATE` query 0 rows match karegi!
* Worker detect karega ki User ne mid-way data change kar diya tha, isliye worker purane AI result ko **silently abort (discard)** kar dega taaki user ka naya data overwrite na ho!
