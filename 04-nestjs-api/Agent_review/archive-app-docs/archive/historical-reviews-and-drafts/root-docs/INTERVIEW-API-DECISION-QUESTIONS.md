# Interview API — Decisions Required Before Coding

## Q1. Route shape

Choose the public command/read paths:

```text
Option A: /api/v1/companies/:companyId/interviews
Option B: /api/v1/applications/:applicationId/interviews
Option C: both (company scheduling + participant self-read)
```

## Q2. Actor permissions

- Who may schedule/reschedule/cancel: owner, employer, HR, interviewer, candidate?
- Can a candidate cancel or request reschedule, or only confirm/decline?
- Must interviewer be an active member of the same company?

## Q3. Status transitions

Approve exact transitions and terminal states from the enum/function in `10_interviews.sql`.
No backward/reopen transition should be invented.

## Q4. Time handling

- Request timezone format and canonical storage timezone.
- DST/invalid-local-time behavior.
- Minimum lead time and past-slot rejection.

## Q5. Notifications and external integrations

- Which approved event contracts trigger interview notifications/reminders?
- Are calendar/video providers current scope or future scope?
- Are reminders generated by existing scheduler or a separate worker?

## Q6. Concurrency and idempotency

- Slot booking must lock the schedule block and prevent overlap.
- Confirm whether a persisted idempotency key exists for schedule commands.

**Until these decisions are frozen, no interview endpoint should be coded.**
